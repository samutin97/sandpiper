# Sandpiper — изменения относительно Hiddify

Sandpiper — изменённая версия приложения **Hiddify** (https://github.com/hiddify/hiddify-app, версия 5.9.8)
под лицензией **Hiddify Extended GPL v3** (см. [LICENSE.md](LICENSE.md)), которая сохраняется для всех изменений.
Авторство исходного приложения принадлежит команде Hiddify. Ядро — форк hiddify-core (ветка `hardened`),
собирается отдельно.

Цель форка — личный некоммерческий клиент для небольшой группы в России: не выдавать адрес VPN-сервера
другим приложениям на телефоне, не отправлять ничего лишнего провайдеру, не позволять чужим приложениям и
ссылкам управлять туннелем. Каждое изменение — отдельный коммит ветки `hardened` (идентификаторы находок —
из внутреннего аудита, он не публикуется). Хеши коммитов в таблицах — из истории разработки до публикации;
если при публикации история пересобиралась (обезличенный автор), в этом репозитории этих хешей может не быть —
содержание изменений от этого не меняется.

## Чего форк НЕ даёт (честно)

- **VPN остаётся видимым.** Android показывает любому приложению факт VPN (`TRANSPORT_VPN`) и интерфейс `tun0`
  (имя задаёт система, изменить нельзя); 13 проверенных приложений (WB, Ozon, МТС, Билайн, Сбер и др.) объявляют
  в `<queries>` интент `android.net.VpnService` и находят **любой** VPN-клиент при любом имени пакета; около 75
  приложений из проверенного набора видят полный список установленных пакетов. Новое имя пакета защищает
  только от поиска по известным именам (как у СберЗдоровья, ищущего `app.hiddify.com`).
- **Исключение из VPN** скрывает от исключённого приложения `TRANSPORT_VPN`, но не `tun0`; строгий фильтр ядра
  (Android 10+) не даёт таким приложениям **пользоваться** туннелем (привязка сокета к `tun0`), но не прячет его.
  На Android 9 и ниже фильтра нет.
- **Собственные запросы приложения** идут через туннель только с hardened-ядром (`protectsOwnSockets`); с
  официальным ядром приложение исключено из своего VPN, и тогда фоновые обновления подписок при подключённом VPN
  не выполняются (ручное — с предупреждением). При выключенном VPN обновление всегда идёт напрямую — только по
  подтверждению или с включённой настройкой.
- **Kill switch** — надёжный только системный («Постоянная VPN» + «Блокировать соединения без VPN»): ядро работает
  в процессе приложения, и его падение (паника Go) завершает весь процесс вместе с TUN; до перезапуска службы
  (`START_STICKY`, обычно секунды; у Android есть нарастающая задержка повторных перезапусков) трафик без системной
  блокировки идёт мимо VPN. Если же ядро остановилось, а процесс жив, служба держит TUN и трафик отбрасывается до
  повторного подключения или «Отключить». При системной блокировке исключённые приложения остаются без сети.
- **QUERY_ALL_PACKAGES** оставлено: оно нужно, чтобы показать список установленных приложений для раздельного
  туннелирования и раскрыть префиксы встроенного списка. Само по себе ничего не передаёт.
- Сканирование QR-кодов — библиотека Google ML Kit (`mobile_scanner`); её возможная телеметрия не проверена.
- Неизменными остались внутренние имена: Dart-пакет `hiddify`, имена каналов `com.hiddify.app/...` (общие с
  iOS/macOS/Windows), Java-пакет ядра `com.hiddify.core` — они видны только тому, кто разбирает код APK (там же
  пути Go-модулей `github.com/hiddify/...` ядра).
- iOS и Linux не собирались и не проверялись. Windows и macOS собирает только CI (раздел «Desktop» ниже), на
  устройствах они не проверялись; часть защит Android на desktop не действует.

## Какой резолвер видит имя VPN-сервера

- **Имена VPN-серверов** (настройка «DNS» → «Резолвер имён серверов», ядро — ключ `server-dns-address`):
  по умолчанию DNS over HTTPS по IP-адресу, без предварительного DNS-запроса — сначала **Cloudflare**
  (`https://1.1.1.1/dns-query`), затем **Quad9** (`https://9.9.9.9/dns-query`), затем **Google**
  (`https://8.8.8.8/dns-query`), при неудаче — системный резолвер. Имя сервера видит первый ответивший из них;
  провайдер видит только TLS-соединение к нему. Если узел в профиле задан **IP-адресом**, DNS-запроса нет вовсе
  (sing-box резолвит только домены). С официальным ядром ключ не действует — имена резолвит прямой резолвер.
- **Российские («прямые») сайты** (настройка «Прямой DNS»): системный резолвер Android (`local`) — при «Частном
  DNS» его оператор, иначе DNS провайдера; третья сторона не добавляется (провайдер видит эти соединения и так).
  Запасного открытого запроса к 8.8.8.8 при `local` больше нет.
- DoH Яндекса — только вариант в настройках. Открытый UDP к публичным резолверам (`udp://1.1.1.1` апстрима) не
  используется.
Серверу подписки рекомендуется отдавать адреса узлов IP-адресами там, где не нужен CDN.

## Публикация и сборки (GitHub Actions)

- Исходники — этот публичный форк (ветка `hardened`) и форк ядра `samutin97/sandpiper-engine` с изменёнными
  подмодулями (см. README). Подмодуль `hiddify-core` указывает на форк ядра, закреплён на его коммите.
- Релизы собирает один workflow `.github/workflows/sandpiper-release.yml` (вручную или по тегу `v<версия>-sp.<n>`):
  ядро — из закреплённого подмодуля (aar, Windows DLL и запускатели, macOS dylib и xcframework туннеля), затем
  тесты и сборки Android (подпись ключом из секретов репозитория, сверка сертификата и проверка манифеста),
  Windows x64 (Setup.exe, portable zip), macOS (dmg, ad hoc); всё — в черновик релиза с `SHA256SUMS.txt`.
- Удалены workflows и скрипты апстрима, публикующие куда-либо или требующие его учётных записей: Google Play,
  TestFlight, Microsoft Store (по расписанию), WinGet, VirusTotal, выгрузка символов в Sentry, подпись Azure/Apple,
  номера сборок iOS, dependabot (ежедневные PR с подмодулем апстрима).
- Ссылка «Исходный код» в «О приложении» ведёт на этот форк (`Constants.forkUrl`).
- Из публичного дерева убраны значения, указывающие на конкретный сервер (пути проверки DpiProbe, порты и подсеть
  в тестовых данных) и пути сборочного ПК.

## Desktop (Windows, macOS)

Сборки делает только CI, на устройствах они **не проверялись**. Ядро desktop — то же hardened-ядро, собранное из
подмодуля (раньше по умолчанию бралось официальное ядро 5.9.8); сборка передаёт приложению
`--dart-define=core_hardened=true` (`CORE_HARDENED=1` в Makefile), и приложение обращается к локальному прокси ядра
с его именем пользователя (`local-proxy-username`), а не `hiddify`.

Изменено для desktop: локальный прокси по умолчанию с паролем, случайные порты mixed и Clash API на установку
(hardened-ядро Clash API вовсе не открывает); предупреждение о системном прокси (системный прокси Windows/macOS
пароль передавать не умеет — порт, на который он указывает, остаётся без пароля); своё окно, мьютекс, VERSIONINFO и
каталог данных `%APPDATA%\Sandpiper` (раздельно с установленным Hiddify); установщик со своим AppId, только для
администратора, удаляет свою службу при удалении; портативная сборка не ставит службу SYSTEM; обработчик ссылок
`sandpiper://` с путём в кавычках, MSIX объявляет только `sandpiper`; профиль VPN на macOS и образ dmg названы
Sandpiper.

Свои имена Windows (5.9.8-sp.4): приложение `Sandpiper.exe`, запускатели ядра `SandpiperCore.exe`,
`SandpiperAdmin.exe`, `SandpiperCoreEngine.exe`, служба `SandpiperAdminBG` (данные и секрет — в
`ProgramData\Sandpiper\AdminBgService`), данные и настройки портативной сборки — `sandpiper_portable_data`;
установщик останавливает и удаляет только свою службу. Фиксированных портов нет: ядро приложения, процесс
движка и служба VPN-режима при каждом запуске берут свободный порт на 127.0.0.1; служба публикует адрес и свой
сертификат в `control.endpoint` рядом с секретом, приложение доверяет только этому сертификату. Sandpiper и
запущенный Hiddify больше не делят ни процессы, ни службу, ни порты, ни каталоги.

Не сделано (план): на macOS — имя приложения, bundle id, ярлык, каталоги и фиксированный порт службы (18420;
от них зависят подпись, системное расширение и скрипты установки); kill switch; шифрование данных профилей;
`hiddify-core.dll` (внутреннее имя библиотеки).

- **Возврат туннеля после гибели процесса (Android).** Кроме `START_STICKY` — сторож: неточный неразбуживающий
  будильник раз в 15 минут (без wake lock), взводится только пока работает туннель, включённый пользователем;
  если служба не работает, запускает её снова (или показывает уведомление, по нажатию на которое туннель
  включается). Любой старт без приложения (перезапуск системой, сторож, «Постоянная VPN») сначала поднимает
  блокирующий TUN (весь трафик отбрасывается), и только потом ядро; не стартовало ядро — блокировка остаётся с
  уведомлением «трафик заблокирован» и кнопкой «Отключить». Окно между гибелью процесса и возвратом не
  закрывается: без «Постоянной VPN» с «Блокировать соединения без VPN» трафик в это время идёт мимо туннеля.
- **«Проверить путь до сервера».** Результат и ход проверки — над полями, форма сворачивается на время проверки,
  на кнопке — секунды. Тестовые пути сервера приходят в заголовке ответа подписки
  `profile-probe: get=<путь>;size=<байт>;post=<путь>;up=<байт>` (строгий разбор: только пути того же хоста из
  ограниченного набора символов, размеры в пределах, до 512 символов; иное молча отбрасывается; из текста
  подписки не читается, в конфиг ядра не попадает), хранятся с профилем и подставляются в диалог; ручной ввод
  остаётся.
- **User-Agent подписки**: `HiddifyNext/<версия> (<ос>) awg31` — токен возможностей в конце (клиент понимает узлы
  AmneziaWG 3.1); часть до токена прежняя. Один UA у всех путей загрузки подписки.
- Диалог импорта всегда говорит, как загрузится подписка (через VPN или напрямую).
- Имена источников в журналах и отчёте без имени апстрима (`infra.CoreService`, `core_service.dart`).
- Windows: свои имена процессов, службы и каталогов (раздел «Desktop»).
- **Desktop рядом с запущенным Hiddify**: ядро приложения и процесс движка слушают свободный порт (как на
  Android), а не 17078/17079 апстрима; служба VPN-режима (Windows, Linux) — свободный порт и новый сертификат при
  каждом старте, адрес и сертификат — в `control.endpoint` в её каталоге (`ProgramData\Sandpiper\AdminBgService`;
  раньше приложение читало секрет из каталога Hiddify), секрет уходит службе только по TLS с этим сертификатом.
- Защита службы: без секрета не работает, новый секрет при каждой установке, каталог только для SYSTEM и
  администраторов (пользователи читают секрет установившего, адрес и метку сборки), без «моста», без
  `enable-full-config`/`log-file` из запроса.
- Причина ошибки запуска ядра видна (раньше — «Invalid UTF-8 byte»); импорт и подключение без ядра говорят «Ядро
  не запущено: <причина>» и запускают ядро заново (раньше — `LateInitializationError`).
- Портативная сборка хранит настройки в своей папке (`sandpiper_portable_data`), оставленные в профиле Roaming
  переносятся; пароль локального прокси на desktop новый при каждом запуске (переключатель «Постоянный пароль»,
  по умолчанию выключен; введённый вручную пароль сохраняется; при раздаче в локальную сеть не меняется).
- Ядро: CLI `run` не открывает Clash API без `clash-api-listen`; журнал локального прокси не пишет присланные при
  неудачной авторизации имя и пароль.
- Ядро: шлюз рукопожатий считает сервер по адресу и с момента TCP-соединения; обращения к подсети TUN не
  выходят с устройства; keep top — только по автогруппе; узлы «по требованию» после пересборки показываются
  непроверенными (подробно — CHANGES-FORK.md ядра).

### 5.9.8-sp.4 — финальные правки
- **Адрес сервера не виден другим приложениям** (проверено на Android 14: `ConnectivityManager.getLinkProperties` от чужого приложения, `dumpsys connectivity`, `ip route`/`ip rule` всех таблиц): маршруты VPN — целые `0.0.0.0/0` и `::/0` плюс подсети самого TUN, исключённых маршрутов нет; сокеты ядра к серверу защищены `VpnService.protect()`. Менять ничего не потребовалось.
- **Рукопожатия при подключении**: одно незавершённое TLS-рукопожатие к серверу за раз, пауза перед каждым 0,7–1,1 с (случайно), не больше 4 за 5 с (ядро); после пересборки туннеля узлы вне автогруппы не проверяются (раньше — пачка рукопожатий и пинги у непроверенных узлов).
- **Android 14: при подключении один SYN на адрес DNS туннеля (порт 853) уходил в Wi-Fi/мобильную сеть** — системная проверка Private DNS новой VPN-сети начиналась до правил, направляющих трафик в VPN. Теперь любой старт службы сначала поднимает TUN без DNS (с тем же списком приложений, что у прошлого TUN ядра), и TUN ядра принимает ту же сеть; если ядро не открыло TUN за 30 с (неудачный старт по нажатию) — блокировка снимается.
- После возврата туннеля без приложения («Постоянная VPN», перезапуск после гибели процесса, сторож) снова разрешаются прямые сайты («Россия напрямую») и проверяется узел AmneziaWG (ядро строило конфиг без интерфейса платформы, DNS «напрямую» спрашивал `[::1]:53`).
- Журнал: датаграммы приложений на адрес DNS туннеля не на порт 53 больше не пишутся как ERROR «DNS packet» на каждую; имя пользователя локального прокси не пишется при неудачной авторизации по HTTP (ядро).
- Портативная сборка Windows не создаёт пустую папку в профиле Roaming (`%APPDATA%\Sandpiper\sandpiper`); пустые папки от прошлых портативных сборок удаляются.
- Подписка через CDN-домен по-прежнему приходит без узла AmneziaWG (CDN меняет User-Agent): клиент не подменяет её содержимое узлом из прошлых обновлений — иначе отзыв узла сервером не дошёл бы до клиента; решается на сервере.

## 5.9.8-sp.5 — выбор варианта по рейтингу сервера
- **Сервер подписки может ранжировать свои варианты** заголовком ответа `profile-policy`: уровни (рекомендуемые, резервные, последний резерв, только вручную) и у каждого варианта три оценки от 1 до 5 — надёжность, маскировка, безопасность — с короткими подписями из фиксированного набора (переводит приложение). Заголовок принимается только из ответа по HTTPS (не из текста подписки), читается строго: мусор отбрасывается целиком, подписка работает как без него. Политика не добавляет узлов, не меняет настроек и не называет хостов: проверки идут только через проверяемый узел к хосту самой подписки и напрямую к этому же хосту.
- **Ядро выбирает вариант само** (группа «По рейтингу сервера»): сверху вниз по уровням, проверяя, что через вариант действительно идут данные (загрузка 64 КиБ тестового файла подписки), а не только рукопожатие. Если передача замирает и путь до сервера по TCP заморожен или режется, ядро сразу переходит на варианты через UDP, не перебирая остальные TCP. Понижение — только после подтверждённого отказа, без сети — никогда; возврат наверх — редкой проверкой в фоне и только после двух успешных подряд. Последний резерв с пометкой сервера включается только после согласия пользователя. Отказы запоминаются по сети (без её имени) на 6 часов.
- **Ручной выбор сильнее**: переключатель «Выбирать по рейтингу сервера» вверху списка вариантов включён, когда сервер прислал рейтинг (один раз переключает с «Наименьшего пинга»); выбор другого варианта выключает его и запоминается.
- **Список вариантов** с рейтингом разбит на «Рекомендуемые», «Резервные варианты», «Последний резерв — используйте, только если остальное не работает» и «Другие варианты»; у варианта — «Надёжность 5 · Маскировка 4 · Безопасность 5» (на узком экране короче) и метка «резерв»/«последний резерв»; в подробностях варианта — шкалы крупнее, подписи сервера и пояснение шкалы. На главном экране — плашка, когда работает резервный вариант (какой и почему), и вопрос перед последним резервом. Без рейтинга от сервера ничего этого нет.
- Обновление подписки, пришедшее без рейтинга (например, через CDN), сохраняет прежний рейтинг до 7 суток (сервер может задать срок); состав вариантов всегда берётся из нового ответа. Пустой рейтинг (`v=1`) снимает его сразу.

### 5.9.8-sp.5 — исправления после проверки на эмуляторе
- Последний резерв (AmneziaWG) после «Использовать» снова включается: узел, через который не открывается тестовый файл подписки, проверяется нейтральной загрузкой через него же (ядро).
- Кратковременный отказ одного варианта больше не лишает резерва надолго: отметки отказов стали приоритетом (отмеченные пробуются после остальных), а не запретом на 6 часов; туннель не остаётся без вариантов (ядро).
- Резерв AmneziaWG, который никто не выбрал, больше не обменивается пакетами с сервером при подключении и в простое (ядро).
- Отказ варианта при работающем туннеле замечается за ~20 с по соединениям приложений, а не только плановой проверкой раз в 10 минут (ядро).
- Оценки в списке вариантов — значками и числами, помещаются на любом экране (названия — в подробностях варианта); порядок в секциях — порядок сервера; на главном экране группа подписана коротко.

## 5.9.8-sp.6 — правила последнего резерва
- **Последний резерв не используется без согласия ни при каком пути**: ни после гибели процесса или аварийного завершения (выбор из кэша исправляется до того, как через туннель пойдёт хоть одно соединение), ни после перезагрузки конфигурации, ни при повторных попытках, ни при смене профиля. Пока вы не решили, соединения нет: вопрос «Остальные варианты не работают. Включить последний резерв?» говорит об этом прямо, «Не сейчас» сворачивает его в строку «Нет соединения: последний резерв ждёт вашего решения» с кнопкой «Использовать», карточка на главном экране показывает «Нет соединения» (ядро и приложение).
- Согласие действует для этого варианта этого профиля при этом рейтинге сервера; другой профиль, новый рейтинг или изменившийся вариант спрашивают снова; остановка подключения сбрасывает его. Нажатие «Использовать» больше не теряется, если ядро в этот момент проверяло варианты выше (ядро).
- Проверка варианта засчитывает только сам тестовый файл: страница ошибки, перенаправление или пустой ответ больше не выдают замёрзший вариант за рабочий (ядро).
- Последний резерв не попадает в «Наименьший пинг» и «Балансировку» и не проверяется в фоне ни при каких настройках (ядро).
- Мелочи: вариант, названный сервером в двух уровнях, относится к более строгому; после смены сети повторные попытки снова идут через минуту, а не через 15; перебор останавливается, как только выбран другой вариант; перевод часов назад не продлевает отметки отказов; надпись «медленно» снимается после возврата к основным вариантам (ядро и приложение).
- Проверка варианта всегда укладывается в своё время, даже если подключение через вариант не возвращается: раньше такая проверка могла остановить выбор по рейтингу, и «Использовать» срабатывало с задержкой (ядро).
